# Recommended Architecture

Instead of hardcoding categories:

```cpp
struct NodeCategory
{
    QString id;
    QString displayName;
    QString icon;
    QColor color;
};
```

Then register nodes dynamically:

```cpp
registerNode<AddNode>("math/basic");
registerNode<ColorBlendNode>("utility/color");
```

This gives:

* plugin extensibility
* searchable hierarchy
* future marketplace support

---

# Strong Recommendation: Default “Quick Nodes”

Users LOVE immediate usability.

Provide:

* constants

out of the box.

That removes friction instantly.

# Suggested Final Default Package

```text
Core
 ├── Math
 ├── Logic
 ├── Utility
 ├── Script
 ├── Events
 ├── Data
 ├── Color
 ├── Network
 ├── Qt
 └── System
```

Yes — you should absolutely have an **Output category**.
Without outputs, node graphs feel incomplete because users can calculate data but not “materialize” it into something visible/audible/exportable.

For a Qt-based editor, outputs can become one of the most powerful parts of the ecosystem.

# VERY IMPORTANT:

# Separate “Generator” vs “Output”

These are different concepts.

---

## Generator Nodes

Produce data.

Examples:

* Sine Wave
* Noise
* Gradient
* Oscillator
* Camera Feed

---

## Output Nodes

Consume final data.

Examples:

* Audio Device
* Video Window
* File Writer
* Stream Output

---

# Example Graph

```text
[Sine Generator]
        ↓
[Gain]
        ↓
[Audio Output]
```

or

```text
[Noise]
   ↓
[Color Gradient]
   ↓
[Viewport Output]
```

This distinction is architecturally VERY important.
